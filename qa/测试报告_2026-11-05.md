### BUG-001: 点地图行后视图不切换，地图详情进不去

- **严重程度**: S1（核心旁路不可用）
- **状态**: 已验证关闭
- **复验轮次**: 0
- **发现方式**: 自动化测试（真机 e2e「地图详情视图」）
- **复现步骤**:
  1. 启动 tern 0.9.11 窗口，开发态链接挂载本插件，打开 Matt 面板
  2. 点击顶部「任务板」按钮，等数据加载完
  3. 鼠标点击地图列表的第一行
- **预期行为**: 进入地图详情，出现地图标题、票号与票数、「子票（N）」小节、「返回任务板」按钮（TC-02-02）
- **实际行为**: 视图停在任务板，点地图行无反应
- **证据**: 宿主侧渲染抛 `host.luau:472: attempt to call a nil value`（被框架吞掉，只表现为"不切换"）。取证方式：pcall 包住渲染分支并把错误串写入共享存储读回
- **环境**: tern 0.9.11 / Windows 10.0.26200 / gh 2.95.0
- **根因分析**: **Verified** —— 地图详情渲染函数调用「取当前选中地图」的辅助函数，但该函数定义在其后；Lua 局部函数在定义语句执行前不存在，函数体里引用到的是全局表里的 nil，调用即抛错。修法：辅助函数移到渲染函数之前。证据 `host.luau:472`（调用点）/ `host.luau:467`（定义点），E3
- **影响范围**: 功能面 —— 地图详情整条路径（子票列表、地图级前沿、迷雾、范围外）不可达，地图行点击/子票点击/地图内键盘三条路径同时失效；数据面 —— 无脏数据；用户面 —— 只能看列表，看不到地图子票与两节正文；安全面 —— 无；修复波及面 —— 仅两函数定义顺序
- **Severity 依据**: 核心功能**旁路**不可用（列表仍可用）→ S1
- **修复建议**: 辅助函数移到渲染函数之前
- **回归建议**: TC-02-02、TC-02-03、TC-02-05、TC-02-06、TC-02-07；e2e「地图详情视图」已固化

### BUG-002: 注入结果回写后提示停在「提交中」，窗口侧戳宿主的事件被丢弃

- **严重程度**: S1（核心旁路降级）
- **状态**: 已验证关闭
- **复验轮次**: 0
- **发现方式**: 自动化测试（真机 e2e「注入结果回写」，偶发红）
- **复现步骤**:
  1. 启动 tern 0.9.11 窗口，打开 Matt 面板（技能视图）
  2. 选中任一技能，点击顶部「注入技能」按钮
  3. 等待 20 秒观察提示文字
- **预期行为**: 提示从「提交中」变为「已提交」或「提交失败」并带出原因（TC-04-01、TC-04-03）
- **实际行为**: 提示长期停在「提交中」；回写数据本身已正确写入（读回可见 `{seq, ok, name, error}`）
- **证据**: 回写数据正确但宿主未重画。窗口侧戳宿主用的节点 id 是编造的 `main.0.refresh`，平台按 id 定位节点，找不到即丢弃事件（`window.luau:233-238`）。E3
- **环境**: tern 0.9.11 / Windows 10.0.26200 / 无活 agent
- **根因分析**: **Verified** —— 两处叠加：① 戳宿主的节点 id 是编造字符串，平台定位不到节点就丢事件，宿主因此不重画；② 工具条「刷新」按钮的动作名与戳宿主用的动作名撞车，即使戳对了也会被当成"用户点了刷新"去重新拉数据。修法：给「刷新」按钮加 key 让节点 id 可寻址；按钮自身动作改名 `reload`，与戳宿主用的 `refresh` 分离。证据 `window.luau:233-238`、`host.luau:622-631`，E3
- **影响范围**: 功能面 —— 注入链路的**结果反馈**环失效（注入本身照常送达或退剪贴板），并波及「刷新」按钮（动作名撞车会让戳宿主误触发重新拉数据）；数据面 —— 无脏数据；用户面 —— 点注入后看不到结论；安全面 —— 无；修复波及面 —— 工具条按钮、戳宿主 id、事件分支分工三处
- **Severity 依据**: 核心功能**旁路**降级（结果反馈失效，注入本身可用）→ S1
- **修复建议**: 「刷新」按钮加 key；按钮动作改名与戳宿主动作分离；戳宿主改用真实节点 id
- **回归建议**: TC-04-01、TC-04-03、TC-07-01、TC-07-04；e2e「注入结果回写」已固化。**修复后必须连跑多次** —— 该缺陷表现为偶发，单次绿不能证明修好

### BUG-003: e2e 用例用固定等待，异步数据落盘时间不定导致随机红

- **严重程度**: S2（测试基础设施可靠性）
- **状态**: 已验证关闭
- **复验轮次**: 0
- **发现方式**: 自动化测试（连续跑 e2e 时不同用例随机失败）
- **复现步骤**:
  1. 连续运行 `bash test/e2e.sh` 三次以上
  2. 观察失败用例不固定
- **预期行为**: e2e 门禁可重复执行，结果稳定
- **实际行为**: 同一份代码连续运行，结果在"全绿"与"某个用例红"之间摇摆
- **证据**: 三次连续运行中两次全绿、一次「地图详情视图」红、另一次「注入结果回写」红。E3
- **环境**: tern 0.9.11 / Windows 10.0.26200
- **根因分析**: **Verified** —— 用例用固定时长睡眠等异步结果（gh 拉取、窗口侧回写），但这些数据落盘时间随机器负载与网络波动；睡眠到期时数据还没到，断言就红。进一步定位到第二层竞态：取列表项坐标与实际点击之间布局可能已变动，点空了表现为"点了没反应"。修法：① 新增「等待条件成立」动作（轮询渲染树直到目标文本出现，超时才判失败）；② 新增「点击直到目标出现」动作（点一次、等一下、目标没出现就再点），把点击做成幂等。证据 `test/e2e-cases.sh` 的 `wait-for` / `click-until` / `click-btn-until`，E3
- **影响范围**: 功能面 —— 不影响产品行为，只影响门禁本身；数据面 —— 无；用户面 —— 开发者跑门禁随机看到红会怀疑产品；安全面 —— 无；修复波及面 —— 只改 e2e 脚本，不动产品代码
- **Severity 依据**: 体验问题（测试基础设施可靠性）→ S2
- **修复建议**: 用条件等待替代固定睡眠；点击做成幂等重试；等待设明确超时上限
- **回归建议**: 连跑 e2e 六次全绿才算修复确认；已固化为门禁 `bash test/all.sh`
