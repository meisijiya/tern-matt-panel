### BUG-001: 点地图行后视图不切换，地图详情进不去

- **严重程度**: S1（核心旁路不可用 —— 地图详情是任务板的核心浏览路径，失效后只能看列表）
- **状态**: 已验证关闭
- **复验轮次**: 0
- **发现方式**: 自动化测试（真机 e2e「地图详情视图」用例）
- **复现步骤**:
  1. 启动 tern 0.9.11 窗口，用开发态链接挂载本插件，打开 Matt 面板
  2. 点击顶部「任务板」按钮，等数据加载完
  3. 鼠标点击地图列表的第一行
- **预期行为**: 进入地图详情，出现地图标题、票号与票数、「子票（N）」小节、「返回任务板」按钮（用例 TC-02-02）
- **实际行为**: 视图停在任务板，点地图行没有任何反应
- **证据**: 宿主侧渲染时抛 `attempt to call a nil value`（`host.luau:472`），但该异常被框架吞掉，只表现为"不切换"。取证路径：用 pcall 包住视图渲染分支并把错误串写入共享存储，读回得到 `host.luau:472: attempt to call a nil value`
- **环境**: tern 0.9.11 / Windows 10.0.26200 / gh 2.95.0 / 本机已装中文技能包
- **根因分析**: **Verified**。地图详情渲染函数调用「取当前选中地图」的辅助函数，但该辅助函数的定义在渲染函数**之后**。Lua 的局部函数在定义语句执行前不存在，渲染函数体里引用到的是全局表里的 nil，调用即抛错。修法：把辅助函数移到渲染函数之前。证据：`host.luau:472`（调用点）与 `host.luau:467`（定义点）——E3（真机复现 + 修复后复验通过）
- **影响范围**:
  - 功能面：地图详情整条路径（子票列表、地图级前沿、迷雾、范围外）全部不可达；地图行点击、地图内子票点击、地图内键盘操作三条路径同时失效
  - 数据面：无脏数据（纯渲染缺陷，不写任何状态）
  - 用户面：面板操作者无法查看地图的子票与两节正文，只能看到地图列表与前沿列表
  - 安全面：无安全影响
  - 修复波及面：仅 `host.luau` 内两个函数的定义顺序，不改行为契约
- **Severity 依据**: 核心功能的**旁路**（任务板浏览）不可用，列表仍可用 → S1
- **修复建议**: 把「取当前选中地图」的辅助函数移到地图详情渲染函数之前
- **回归建议**: TC-02-02（点地图行进地图详情）、TC-02-03、TC-02-05、TC-02-07、TC-02-06；真机 e2e「地图详情视图」已固化

### BUG-002: 注入结果回写后提示停在「提交中」，窗口侧戳宿主的事件被丢弃

- **严重程度**: S1（核心旁路降级 —— 注入本身仍成功，但用户永远看不到结论，只能靠"提示不变"猜）
- **状态**: 已验证关闭
- **复验轮次**: 0
- **发现方式**: 自动化测试（真机 e2e「注入结果回写」用例，偶发红）
- **复现步骤**:
  1. 启动 tern 0.9.11 窗口，打开 Matt 面板（技能视图）
  2. 选中任一技能，点击顶部「注入技能」按钮
  3. 等待 20 秒观察提示文字
- **预期行为**: 提示文字从「提交中」变为「已提交」或「提交失败」并带出原因（用例 TC-04-01、TC-04-03）
- **实际行为**: 提示文字长期停在「提交中」；回写数据本身已正确写入共享存储（读回可见 `{seq, ok, name, error}`）
- **证据**: 回写数据正确但宿主未重画 —— 读共享存储可见 `inject_result` 已是失败结果，而界面提示未变。窗口侧戳宿主时用的节点 id 是 `main.0.refresh`（编造），平台按 id 定位节点，找不到就丢弃事件（`window.luau:233-238`）。E3（真机复现 + 修复后复验通过）
- **环境**: tern 0.9.11 / Windows 10.0.26200 / 测试窗口旁无活 agent（注入走剪贴板退路）
- **根因分析**: **Verified**。两处叠加：① 窗口侧写完回写数据后要"戳"宿主重画，用的节点 id 是编造的字符串，平台按 id 定位节点，找不到就丢弃 —— 宿主因此永远不重画，提示停在「提交中」；② 宿主工具条上的「刷新」按钮动作名与戳宿主用的动作名撞车（都叫 refresh），即使戳对了也会被当成"用户点了刷新"去重新拉数据。修法：给「刷新」按钮加 key 让节点 id 可寻址，按钮自身动作改名 reload 与戳宿主用的 refresh 分离。证据：`window.luau:233-238`、`host.luau:622-631` —— E3
- **影响范围**:
  - 功能面：注入链路的**结果反馈**这一环失效（注入本身照常送达或退剪贴板）；同时也波及工具条「刷新」按钮 —— 动作名撞车会让"戳宿主"误触发重新拉数据
  - 数据面：无脏数据（回写数据写入正确，只是没被读走）
  - 用户面：面板操作者点注入后看不到结论，无法判断是否成功
  - 安全面：无安全影响
  - 修复波及面：`host.luau` 工具条按钮（加 key + 改动作名）、`window.luau` 戳宿主的 id、宿主事件处理里两个动作分支的分工
- **Severity 依据**: 核心功能**旁路**降级（结果反馈失效，注入本身可用）→ S1
- **修复建议**: 给「刷新」按钮加 key（节点 id 变为可寻址），按钮自身动作改名与戳宿主动作分离；窗口侧戳宿主改用该按钮的真实节点 id
- **回归建议**: TC-04-01、TC-04-03、TC-07-01、TC-07-04；真机 e2e「注入结果回写」已固化。注意：修复后必须连跑多次 —— 该缺陷表现为偶发，单次绿不能证明修好

### BUG-003: e2e 用例用固定等待，异步数据落盘时间不定导致随机红

- **严重程度**: S2（测试基础设施的体验/可靠性问题 —— 门禁随机红会让人不再信任门禁）
- **状态**: 已验证关闭
- **复验轮次**: 0
- **发现方式**: 自动化测试（连续跑 e2e 时不同用例随机失败：一次「地图详情视图」红，一次「注入结果回写」红）
- **复现步骤**:
  1. 连续运行 `bash test/e2e.sh` 三次以上
  2. 观察失败用例不固定（地图详情视图 / 注入结果回写 交替出现）
- **预期行为**: e2e 门禁可重复执行，结果稳定
- **实际行为**: 同一份代码连续运行，结果在"全绿"与"某个用例红"之间摇摆
- **证据**: 三次连续运行中两次全绿、一次「地图详情视图」失败（找不到「返回任务板」）、另一次「注入结果回写」失败（找不到「提交失败」）—— E3
- **环境**: tern 0.9.11 / Windows 10.0.26200
- **根因分析**: **Verified**。用例用固定时长睡眠等异步结果（gh 拉取、窗口侧回写），但这些数据的落盘时间随机器负载与网络波动，不固定。睡眠到期时数据还没到，断言就红。修法：新增"等待条件成立"的动作 —— 轮询渲染树直到目标文本出现，超时才判失败；把相关用例的固定睡眠换成条件等待。证据：`test/e2e-cases.sh` 的 `wait-for` 动作 —— E3
- **影响范围**:
  - 功能面：不影响产品行为，只影响门禁本身
  - 数据面：无
  - 用户面：开发者/评审者跑门禁时随机看到红，会怀疑产品有问题
  - 安全面：无
  - 修复波及面：只改 e2e 脚本，不动产品代码
- **Severity 依据**: 体验问题（测试基础设施可靠性），不影响产品功能 → S2
- **修复建议**: 用条件等待（轮询到目标文本出现）替代固定睡眠；给等待设置明确超时上限，超时才算失败
- **回归建议**: 连跑 e2e 三次全绿才算修复确认；已固化为门禁的 `bash test/all.sh`
